# Размещение Vector на виртуальном сервере

## Рекомендуемый вариант для текущей версии

Текущая версия Vector является клиентским React/Vite-приложением. Для демонстрационного размещения достаточно:

1. Собрать проект командой `pnpm build`.
2. Загрузить содержимое папки `dist` на виртуальный сервер.
3. Раздавать статические файлы через Nginx.
4. Подключить домен и HTTPS.

Docker, PM2 и постоянно работающий процесс Node.js для текущей версии не требуются. Команда `vite preview` предназначена только для локальной проверки сборки и не должна использоваться как production-сервер.

## Ограничения текущей архитектуры

Такое размещение подходит для демонстрации или индивидуального использования, но не превращает приложение в полноценную многопользовательскую систему:

- задачи, документы, сообщения, настройки и вложения хранятся в IndexedDB браузера;
- каждый браузер и компьютер получает собственную независимую базу;
- данные между пользователями и устройствами не синхронизируются;
- чат между пользователями на разных устройствах не работает как серверный чат;
- логины и пароли находятся в клиентском коде;
- проверка пароля и прав выполняется в браузере и не является серверной защитой;
- резервные копии создаются и восстанавливаются вручную в браузере.

Публично размещенную демонстрационную версию нельзя использовать для хранения реальных персональных, финансовых или конфиденциальных документов.

## Минимальная конфигурация VPS

Для демонстрационного варианта достаточно:

- актуальной Ubuntu Server LTS или Debian;
- 1 vCPU;
- 1 ГБ RAM, если сборка выполняется локально или в CI;
- 2 ГБ RAM, если проект собирается непосредственно на сервере;
- 10–20 ГБ SSD;
- статического публичного IP-адреса;
- домена вида `vector.example.ru`;
- Nginx;
- HTTPS-сертификата;
- SSH-доступа по ключу.

Рекомендуется выделить отдельный поддомен. Текущая сборка использует базовый путь `/`. Для размещения по адресу вида `example.ru/vector/` потребуется настроить параметр `base` в Vite.

## Сборка проекта

Сборку желательно выполнять локально или в CI, а на сервер передавать только готовую папку `dist`. Все команды `pnpm` нужно запускать из корня проекта — из каталога, где находятся `package.json` и `pnpm-lock.yaml`:

```bash
cd /path/to/vector
pnpm install --frozen-lockfile
pnpm test
pnpm build
```

Результат сборки появится в каталоге `dist`.

Перед публикацией следует проверить production-сборку локально:

```bash
pnpm preview
```

## Размещение файлов

На сервере можно использовать следующую структуру:

```text
/var/www/vector/current
```

В каталог `current` необходимо загрузить содержимое локальной папки `dist`, включая `index.html` и каталог `assets`.

Для более надежных обновлений рекомендуется хранить сборки в отдельных каталогах и переключать символическую ссылку `current` только после успешной загрузки:

```text
/var/www/vector/
├── releases/
│   ├── 2026-09-01-1200/
│   └── 2026-09-02-0930/
└── current -> releases/2026-09-02-0930/
```

Это позволяет быстро вернуться к предыдущей версии.

## Конфигурация Nginx

Пример файла `/etc/nginx/sites-available/vector`:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name vector.example.ru;
    root /var/www/vector/current;
    index index.html;

    location /assets/ {
        try_files $uri =404;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }

    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header X-Frame-Options "DENY" always;
}
```

Замените `vector.example.ru` фактическим доменным именем.

Включение конфигурации:

```bash
sudo ln -s /etc/nginx/sites-available/vector /etc/nginx/sites-enabled/vector
sudo nginx -t
sudo systemctl reload nginx
```

## Домен и HTTPS

В DNS необходимо создать запись `A`, указывающую поддомен на IPv4-адрес VPS. При использовании IPv6 также создается запись `AAAA`.

После того как сайт станет доступен по HTTP, можно выпустить сертификат Let's Encrypt через Certbot:

```bash
sudo certbot --nginx -d vector.example.ru
sudo certbot renew --dry-run
```

После настройки необходимо проверить автоматическое перенаправление с HTTP на HTTPS.

## Базовая защита VPS

Оставьте открытыми только SSH, HTTP и HTTPS:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status
```

Дополнительно рекомендуется:

- запретить вход в SSH под `root`;
- отключить парольный вход в SSH после проверки доступа по ключу;
- использовать отдельного непривилегированного пользователя для развертывания;
- включить автоматические обновления безопасности;
- регулярно проверять свободное место и журналы Nginx;
- не хранить ключи, пароли и `.env`-файлы в Git;
- сохранять предыдущую рабочую сборку для отката.

## Проверка после публикации

После каждого обновления необходимо проверить:

1. Открытие приложения по HTTPS.
2. Отсутствие ошибок сертификата.
3. Загрузку JavaScript и CSS без ошибок 404.
4. Вход в демонстрационную учетную запись.
5. Переходы по разделам приложения.
6. Создание и редактирование тестовой задачи.
7. Сохранение данных после перезагрузки страницы.
8. Создание и восстановление тестовой резервной копии.
9. Отсутствие ошибок в консоли браузера.
10. Ответы Nginx и отсутствие критических ошибок в `/var/log/nginx/error.log`.

Необходимо помнить, что сохранение данных после перезагрузки подтверждает только работу IndexedDB в данном браузере, но не серверное хранение.

## Архитектура для промышленной версии

Для полноценного многопользовательского использования рекомендуется перейти к следующей схеме:

```text
Интернет
   │
   ▼
Nginx и HTTPS
   ├── статический React-интерфейс
   └── /api → backend-приложение
                 ├── PostgreSQL
                 ├── файловое или S3-совместимое хранилище
                 ├── серверная аутентификация
                 └── журналирование и фоновые задачи
```

Минимально потребуется реализовать:

- серверный API;
- PostgreSQL для пользователей, задач, справочников, документов и сообщений;
- серверное или S3-совместимое хранение вложений;
- хеширование паролей с помощью Argon2id или bcrypt;
- серверную проверку ролей и прав доступа;
- защищенные сессионные cookies с флагами `HttpOnly`, `Secure` и `SameSite`;
- ограничение попыток входа;
- серверный аудит действий;
- проверку типов и размеров загружаемых файлов;
- регулярные зашифрованные резервные копии вне основного VPS;
- мониторинг доступности, ошибок и заполнения диска;
- механизм миграции локальных резервных копий Vector в серверную базу.

Для такой версии удобен Docker Compose с отдельными сервисами Nginx, backend и PostgreSQL. Однако добавлять контейнеризацию только ради текущего статического frontend-приложения необязательно.

## Итоговая рекомендация

Для демонстрации следует использовать статическую сборку `dist`, Nginx, отдельный поддомен и HTTPS. Для реальной совместной работы нескольких сотрудников сначала необходимо добавить backend, централизованную базу данных, серверную аутентификацию и резервное копирование.
